# تصمیم‌های طراحی مرحله صفر

## ارزیابی نسخه موجود

### قابل استفاده دوباره

- استقرار ساده PHP 8.3 و MariaDB روی هاست فعلی؛
- session، CSRF، password hashing و چارچوب RBAC؛
- schema پایه کالا، شرکت، فرصت، پیشنهاد، مسیر، بیمه، فایل و نسخه سند؛
- DECIMAL برای پول/مقدار، foreign key و audit؛
- front controller و جداسازی وب‌روت از secretها.

### نیازمند جایگزینی یا بازطراحی

- رابط فعلی با یک config عمومی، فهرست و modal CRUD ساخته شده و context معامله را حفظ نمی‌کند؛
- endpoint عمومی `resources/{name}` منطق و قرارداد هر workflow را کم‌رنگ کرده است؛
- داشبورد card-based فاقد inbox، next action، waiting state و دلیل توقف است؛
- مدل مفهومی Decision، next-action contract، checklist بررسی و comparison set صریح نیست؛
- صفحات پرونده کالا/شرکت و document review flow در UI واقعی شکل نگرفته‌اند؛
- بخشی از schema درخواست مادر (الزامات، روابط چندگانه، فایل‌های متصل و خروجی AI قابل تأیید) کامل نیست.

## جهت بصری Prototype

«اتاق عملیات آرام»: زمینه روشن گرم، جوهر سبز عمیق، accent مسی محدود، تراکم اطلاعات حرفه‌ای و hierarchy مبتنی بر وضعیت. رنگ فقط برای معناست: قرمز = عقب‌افتاده/مسدود، کهربایی = انتظار/انقضا، آبی = نیازمند تأیید، سبز = تأییدشده/پیش‌رو، خاکستری = نامشخص.

از کارت‌های KPI کلیشه‌ای، modalهای تو در تو و فرم بلند اجتناب شده است. داده در قالب work queue، health strip، timeline، comparison matrix و relationship panels نمایش داده می‌شود.

## تصمیم فناوری

در مرحله صفر فناوری تغییر نمی‌کند. Prototype با HTML/CSS/JavaScript بدون build و بدون dependency است. برای نسخه اجرایی بعدی دو مسیر قابل بررسی است:

1. حفظ PHP monolith و ساخت controller/serviceهای workflow-specific با frontend ماژولار؛ کم‌ریسک‌ترین گزینه برای هاست فعلی.
2. افزودن ابزار build سبک (مثلاً Vite) فقط اگر component complexity و تست UI آن را توجیه کند؛ مهاجرت Laravel/React اکنون مزیت اثبات‌شده‌ای نسبت به هزینه استقرار ندارد.

پیشنهاد فعلی: ابتدا قراردادهای workflow و endpointهای پرونده‌ای در PHP تثبیت شوند؛ انتخاب framework پس از تأیید prototype انجام شود.

## فرض‌های حل‌شده

- دو شریک هر دو می‌توانند مالک یا بازبین باشند؛ separation of duties برای صدور سند از طریق permission حفظ می‌شود.
- تاریخ Prototype نمایشی است؛ نسخه اجرایی UTC/استاندارد ذخیره و جلالی نمایش می‌دهد.
- «منتظر پاسخ» وضعیت عملیاتی است، نه مرحله جدید workflow.
- سلامت پرونده از completeness rules و رکوردهای واقعی محاسبه می‌شود، نه درصد دستی.
- داده Prototype واقع‌نما ولی کاملاً ساختگی و تأییدنشده است.

## موارد واقعاً نیازمند تصمیم کاربر در مرحله بعد

1. مراحل استاندارد شرکت و شروط عبور هر مرحله دقیقاً چیست؟
2. صدور PI/LOI به تأیید هر دو شریک نیاز دارد یا یک نقش مجاز کافی است؟
3. اولویت مالی شرکت در comparison چیست: landed cost، نقدینگی، زمان یا ریسک طرف؟ این انتخاب بر رتبه‌بندی اثر می‌گذارد.
4. سطح محرمانگی آیا فقط team/restricted است یا پرونده خصوصی برای مالک نیز لازم است؟

این پرسش‌ها مانع بررسی شکل و جریان Prototype نیستند.

## محدودیت مرحله صفر

هیچ migration، API، authentication، CRUD یا تغییر در اپلیکیشن production انجام نشده است. `design-preview/` مستقل و داده‌ها داخل JavaScript صرفاً برای نمایش طراحی هستند.
